# ADR 0002：运行日志与操作审计分离

- 状态：已记录的实施方案（尚未实现；保存策略上线前确认）
- 日期：2026-10-23
- 范围：API、后台任务、Agent 和审计边界
- 关联：[日志设计](../logging.md)、[开发规范](../development.md)

## 背景

用户要求在开发前补充日志设计，并要求优先复用成熟能力、不凭空假定。当前 Fastify 日志关闭，只有框架和启动提示，不能据此认为已经具备请求追踪与审计。

## 决策

1. 运行日志复用 Fastify 的 Pino，NestJS 通过官方日志接口接入同一实例；只增加必要的配置和业务衔接，不自建日志库。
2. 运行日志采用统一字段的逐行 JSON 和标准输出，部署环境负责收集与轮转；一期不强制增加集中日志服务。
3. 审计使用 PostgreSQL 独立追加表与独立权限。平台数据库的受保护变更和成功审计在同一事务；受审计的只读操作、登录和外部副作用先持久化意图，再按执行阶段追加结果，不能假设跨系统事务成立。
4. 服务端生成请求标识，跨任务显式传递必要关联；完整追踪按需使用 OpenTelemetry。日志上下文不作为授权依据。
5. 字段采用允许列表并默认脱敏，不记录业务正文、查询结果、凭据和 AI 对话。运行日志可有受控降噪，审计不采样。
6. 保存周期与容量按用户明确回复，留到上线前确认；不会把未提供的数值写成已接受的要求。

## 取舍

- 复用 Pino 与现有技术栈，减少维护和部署负担；代价是需验证 NestJS / Fastify 集成、脱敏和输出故障行为。
- 把全部运行日志写进 PostgreSQL 会让日志吞吐与业务存储耦合；审计有持久化和事务要求，因此单独使用数据库。
- 起步即强制集中日志平台增加自托管负担，尚无实际规模依据；以后可从标准输出接入成熟采集工具。
- 异步输出不能保证异常断电时零丢失；追加表也不等于防篡改存储，不能作超出实现能力的承诺。

## 后续验证

按 [日志设计的验收要求](../logging.md#8-落地顺序与验收) 验证请求关联、并发隔离、敏感信息、事务审计、慢输出和资源上限。依赖兼容性、容量和性能用当前版本及实际测量确认；无法查明且影响实现的事项先向用户确认。
