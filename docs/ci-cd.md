# CI/CD 规则

状态：2026-10-23。**CI 已配置，需推送后验证 GitHub 实际运行；CD 为确定的实施规则，当前没有发布或部署工作流。** 当前已有前后端开发骨架，业务包的静态检查、类型检查、测试和构建均接入统一检查。

CI 是每次提交的自动检查；CD 是将通过检查的版本制作成制品、发布并部署。检查通过不等于获得合并或上线授权。

## 1. 工具链与本地入口

- Node.js 版本见 [.node-version](../.node-version)，当前选择支持期内的 24 LTS。
- pnpm 精确版本见根 [package.json](../package.json) 的 `packageManager`。工具和依赖升级通过 PR，提交对应锁文件和验证结果。
- CI 使用 GitHub 托管的 `ubuntu-24.04`，按锁文件安装。当前工具不需要依赖安装脚本，因此关闭生命周期脚本；后续包确需构建依赖时，单独审查白名单并更新安装规则。

```bash
pnpm install --frozen-lockfile --ignore-scripts
pnpm check
```

| 命令                       | 当前实际检查                                |
| -------------------------- | ------------------------------------------- |
| `pnpm format:check`        | Prettier 检查文档、配置、脚本和应用源码     |
| `pnpm lint:docs`           | Markdown 结构与格式                         |
| `pnpm check:repo`          | 本地 Markdown 链接及锚点、YAML 和工作流策略 |
| `pnpm test:tooling`        | 仓库、工作流和中文 PR 检查工具的回归测试    |
| `pnpm check:workspaces`    | 检查业务包配置，存在时依次执行真实检查      |
| `pnpm audit:deps`          | 查询依赖漏洞通告，高危及以上失败；需要网络  |
| `pnpm check:pr <事件文件>` | 检查事件 JSON 中 PR 的中文标题与正文        |

`pnpm check` 运行表中前五项，无需访问生产服务或真实模型。外部网页不纳入链接检查，避免网络波动影响本地文档检查；其内容仍由评审者核对。

修改工作流还需使用 actionlint 1.7.12 检查：

```bash
actionlint .github/workflows/ci.yml
```

CI 从官方发布下载 actionlint，并校验仓库固定的 SHA-256。更新版本时同时核对校验值；禁止运行未固定版本的远程安装脚本。

## 2. 当前 GitHub CI

[CI 工作流](../.github/workflows/ci.yml) 在以下事件运行：

- PR 创建、代码更新、重新打开、标题或正文编辑、转为可评审。
- 推送到 `main`、合并队列检查，以及手动触发。

稳定的必需检查名为 **`quality`**，来源为 **CI** 工作流。启用分支保护时选择这项检查。工作流不使用路径过滤，也不因文档变更跳过整个检查。

检查顺序：固定工具链 → 冻结锁文件安装 → PR 中文标题与正文 → `pnpm check` → 开发 Compose 配置校验 → 依赖漏洞审计 → actionlint。任何一步失败，整个检查失败；任务有超时，新 PR 提交会取消过时检查，`main` 检查不互相取消。

PR 标题和正文使用中文，标题保留 Conventional Commits 前缀，如 `feat(scene): 新增场景分组命令`。使用 squash merge，并将标题用作合并提交标题。单个历史提交格式暂不由 CI 强制，填写规则见 [中文 PR 与 AI 提交流程](pull-requests.md)。

PR 事件运行 `pnpm check:pr`，从 `GITHUB_EVENT_PATH` 读取标题和正文，检查标题格式、中文描述以及正文中的实际中文说明。模板标题、注释、代码、网址和勾选清单不计入正文。它只能拦截常见漏填与纯英文内容，说明是否准确完整仍需评审。Dependabot 等机器人的 PR 也适用，合并前由维护者改写为中文。其他事件跳过这项元数据检查，脚本的回归测试仍由 `pnpm check` 执行。

依赖审计无法连接服务时视为检查未完成，需重试，不能通过 `|| true` 放行。依赖问题修复或正式替代前，不把检测失败改成成功。

## 3. 新业务代码的接入门槛

应用放在 `apps/*`，共享包放在 `packages/*`。每个工作区包必须有自己的 `package.json`，并提供能实际执行的：

| 脚本        | 要求                                                   |
| ----------- | ------------------------------------------------------ |
| `lint`      | 检查该包源码，新增 TypeScript 时一并落地静态规则       |
| `typecheck` | 使用真实类型配置检查该包及其契约                       |
| `test`      | 测试可观察行为、边界及回归风险，不能全局允许无测试通过 |
| `build`     | 构建该包可交付的输出，不以类型检查或占位命令替代       |

根检查会发现业务源码与包清单，缺少清单或脚本直接失败，然后先按工作区依赖顺序执行 build，再依次执行 lint、typecheck、test；构建失败立即停止，不能靠已有 `dist` 绕过。当前无业务包时明确报告“文档阶段”，不能称为业务测试或构建通过。

工作区配置必须覆盖 `apps/*` 和 `packages/*`，当前检查拒绝排除或遗漏这些目录。调整目录布局时，同步修改工作区配置、检查工具和文档，并验证没有包被漏跑。

脚本检测只能拦截常见漏配和占位；维护者仍需确认检查覆盖实际源码。禁止把业务代码放在检查范围外，禁止新增 `--if-present`、`--passWithNoTests`、无条件跳过或吞掉错误。

评审还需核对 [开发规范](development.md) 中的成熟方案复用、事实依据、简洁注释和用户确认记录。日志改动按 [日志设计](logging.md#8-落地顺序与验收) 补充脱敏、关联、审计与资源验证；文档设计完成不等于这些运行能力已实现，静态检查也不能替代语义评审。

当前使用 TypeScript 6.0.3、ESLint 10、typescript-eslint 和 Vitest 5，具体精确版本以根清单与锁文件为准。TypeScript 保持在 typescript-eslint 支持范围内，升级时先检查兼容性。共享严格配置见 [tsconfig.base.json](../tsconfig.base.json) 和 [eslint.config.mjs](../eslint.config.mjs)。前端使用 Testing Library + jsdom 验证交互，后端使用真实 Fastify 注入验证请求链路；浏览器关键流程后续接入 Playwright。

日常检查使用供应商模拟、固定数据和隔离测试服务。权限、缓存、迁移、Fastify 请求链路及场景命令按 [开发规范](development.md) 增加集成验证。数据库集成测试使用临时数据库，测试完成后清理。

未来拆分多个 CI 任务时，保留始终执行的最终门禁，显式要求预期任务均为成功；`skipped`、取消或缺失不得算通过。

## 4. 工作流权限与供应链

- PR 检查只授予 `contents: read`，不读取部署或生产 secrets，不使用自托管 runner。
- checkout 使用 `persist-credentials: false`，不保留可用于后续 Git 操作的凭据。
- 所有远程 Action 固定完整提交 SHA，旁注版本方便审核；Docker Action 固定镜像 digest。Dependabot 定期提出更新，由维护者审核。
- 禁止通过 `pull_request_target` 或带写权限的后续任务执行 PR 中的代码、脚本和制品。
- PR 标题和正文从 GitHub 事件 JSON 文件读取，仅作为数据处理，不拼接到 shell 源码。
- 发布写权限只授予受信发布任务；不同用途使用最小权限，不能为了方便将整个 CI 改为写权限。
- 普通 CI 不部署、不发布、不自动合并。缓存不能包含凭据和敏感查询结果。

## 5. GitHub 必须单独启用的设置

下表是维护者操作清单，**这些设置不会因为提交本文件自动生效**。

| 设置                  | 规则                                                                          |
| --------------------- | ----------------------------------------------------------------------------- |
| 默认分支              | `main`                                                                        |
| `main` Ruleset / 保护 | 通过 PR 合入；禁止删除和强推；要求解决评审对话                                |
| 必需检查              | CI 的 `quality`；要求基于最新主线或通过合并队列验证                           |
| 审批                  | 当前单人：0 人批准，PR 与 CI 必需；有独立协作者后改为非作者 1 人并撤销旧批准  |
| 合并方式              | 启用 squash merge，合并提交标题使用 PR 标题                                   |
| 规则归属              | 维护者确定后添加有效 CODEOWNERS；优先覆盖 `.github/`、权限、查询和迁移        |
| Actions 权限          | 默认只读；外部首次贡献者执行工作流需审核；仅允许信任的 Action                 |
| 安全功能              | 启用可用的 Dependabot alerts、secret scanning / push protection、私密漏洞报告 |
| 发布环境              | CD 实现时再创建所需环境；启用非发起者审批需有另一位真实审批人，并限制来源     |
| 标签保护              | 保护 `v*`，限制创建者，禁止修改和删除已发布标签                               |

审批功能受仓库可见性和 GitHub 套餐影响。功能不可用时先维持人工审核、手动发布，不声称获得相同的自动保护。GitHub 文档说明了 [保护环境](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) 和 [工作流安全](https://docs.github.com/en/actions/reference/security/secure-use) 的具体配置。

按页面操作的步骤见 [GitHub 仓库设置](github-setup.md)。用户已确认单人审批为 0；这不会取消 PR、`quality`、主线同步或解决评审对话的要求。

## 6. CD：首个可运行版本的发布规则

当前不配置占位的“发布成功”任务。首次正式版本前，需在 PR 中实现并验证以下流程，再启用 CD：

1. **准备版本 PR。** 明确版本号、许可证、更新说明、兼容范围、迁移、部署及回滚办法。应用版本采用 SemVer；主题、组件与场景格式分别声明兼容版本。
2. **固定源码。** 只从受保护 `main` 上检查成功的确定提交准备发布。手动指定该提交和版本，校验提交归属、版本一致及标签不存在。
3. **准备可审阅制品。** 在无发布写权限的构建任务执行完整检查、测试和构建，生成制品、校验和、依赖清单及来源信息。测试数据不得包含生产凭据。
4. **审核后发布。** `release` Environment 的审核者核对提交、检查及制品。发布任务只发布刚才构建的固定制品，创建版本标签和 GitHub Release；需要容器时发布到 GHCR，并记录不可变 digest。审批后不重新获取浮动源码或重新构建另一份制品。
5. **分别部署。** 版本发布不自动更新用户的自托管实例。项目自己的演示/生产部署需要明确目标，并通过独立环境规则；生产默认人工批准。

发布任务限定最小的 `contents: write`、必要时的 `packages: write`；需要外部云身份时优先短期身份，不在仓库保存长期密钥。审批依赖真实配置的 Environment，不能只在 YAML 中写出名字。

不可变版本不覆盖发布；修复使用新版本。发布失败可以重试原制品，不能静默替换同一版本的内容。主题和代码扩展采用相同的版本、兼容和来源追踪原则。

## 7. 部署、回滚与变更证据

- 部署前核对健康检查、配置、数据库备份、迁移顺序和旧版本兼容性；生产密钥只放受保护环境。
- 优先采用向后兼容、可分阶段完成的迁移。不可逆数据变更必须有单独恢复方案，不能把“回退镜像”等同于数据恢复。
- 部署后检查健康、核心接口、授权查询和大屏加载；失败时回到上一版固定制品。数据库按已审阅方案恢复或前向修复。
- 记录版本、提交、制品 digest、迁移、操作者、时间、验证及回退结果。示例环境不得连接真实客户数据。
- 当前没有远端部署目标、制品或服务器变更；这些能力随可运行版本落地，状态更新到 [路线图](roadmap.md) 和 [迭代记录](iterations/README.md)。
